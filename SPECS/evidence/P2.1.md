## Deviations and findings

- T03: `FORCE ROW LEVEL SECURITY` also applies to the owner role, so the T04 seed must `SET app.scope = 'platform'` before inserting. `users` has no `tenant_id`, so it has no RLS (the request context reads it before any scope exists). The spec does not name `updated_by`/`published_by` columns' type; they are `NOT NULL` foreign keys to `users`. The runner imports `pg` through the dashboard package, so no root dependency was added.
- T04: the T02 healthcheck probed Postgres over its unix socket, so `pg_isready` passed during the image's temporary init-time server and `db:migrate` hit "Connection terminated unexpectedly" on the first run. `compose.yaml` now probes over TCP (`-h 127.0.0.1`); three fresh resets after the fix were clean.
- T04: `t_broken` and `u_broken_admin` are not seeded; the failure fixtures stay static files.
- T05: `specs/db.spec.ts` needs Postgres (`pnpm db:up`), so `pnpm nx test @byteflock/admin-dashboard` now fails without Docker until T13 makes `pnpm verify` start the database. `withScope` takes a `DbScope` (`{scope:'tenant', tenantId} | {scope:'platform'}`) that the T06 `RequestContext` union will satisfy; the existing tenant-only `RequestContext` is unchanged until T06.
- T06: the seed now also creates `t_broken` and `u_broken_admin` (tenant and membership only; no widget key, draft or revision). Without them the dev session could not sign in as the failure-fixture tenant once the context came from the database, and the P1.6 T-03 e2e test needs it. Decided by the product owner: keep it seeded, and T10 filters the failure-fixture tenant out of the `/platform` tenant list so it shows the three real tenants (spec "three tenants" and P2.1-AC05 stay true).
- T06: a super admin who opens `/` or `/settings/**` is redirected to `/platform`, which does not exist until T10 (404 in the meantime). The six existing own-tenant API routes refuse platform scope with 403 until T10 adds routes that name a tenant. `locale` now comes from `users.locale`, not the tenant fixture.
- T06: `specs/index.spec.tsx` mocks `request-context`, because the page now reaches Postgres and `pg` does not load under jsdom. Dashboard specs may import `pg` (lint exemption for `specs/**`) to arrange test data as the owner role. Suites share byteflock_test and run in parallel, so each test that mutates data uses its own throwaway rows.
- T07: Postgres `jsonb` does not keep key order, so a theme document read back from the database has different key order than the fixture file. Materialised documents are therefore written with sorted keys; the generator `tools/scripts/generate-widget-fixtures.mjs` still writes fixture order. The byte-for-byte match with `validation/widget-fixtures` (T04 done-when) was closed in T08: the generator is canonical too and the fixtures were regenerated.
- T07: the e2e helper now recreates the dashboard database (`byteflock`, the one `next dev` uses) between suites, as it used to wipe local drafts and widget files; T15 moves the tests to `byteflock_test`. The `/dev/session` switcher still lists tenant admins only; platform and agent users arrive in T12.
- T08: `pnpm db:reset` does not run `db:materialise` yet; T13 wires `stack:reset` to `db:reset`, `db:seed` and `db:materialise` (P2.1-AC11). Until then `pnpm stack:reset` still copies the fixtures.
- T09: the home page heading is now `home.title` (default "<tenant name> support"), so the P1.6 smoke test expects "Acme Corp support" instead of "Admin dashboard". The guard lives in `src/lib/tenant-config.ts` rather than `src/server/tenant-config/` because the editor form also runs it in the browser; the server-only module gating is in `src/server/tenant-config/`. The `agent` role is exercised end to end since T12.
- T10: axe found a real defect in the T09 editor that T09's own axe runs did not hit: the two module checkboxes had no accessible name (`aria-toggle-field-name`, serious) when the module was off. They now carry an `aria-label`. The DB-backed unit suites also got `jest.setTimeout(60_000)`: their setup recreates, migrates or seeds a database and exceeded Jest's 5 s default once, under a repo-wide parallel run.
- T11: the spec's `selector` option was not enough on its own. The bridge variables are `var()` references resolved at `:root`, so the bridge generator now also declares them on `[data-tenant-preview]`; that edits a generated file in `libs/ui-react` (regenerated and committed). The widget-playground e2e suite was not rerun: nothing it uses changed.
- T12: on a cold `next dev`, the switcher page reloaded repeatedly while routes compiled and swallowed the first click (seen once, running three spec files alone). The new spec warms its routes in `beforeAll` and its `signInAs` retries up to three times until the browser leaves `/dev/session`, like the existing `gotoHydrated` helper. The same reload made two T11 chrome-scope tests fail once in a full run (aborted navigation, destroyed page context): a new `gotoSettled` helper retries the navigation and those steps are wrapped in `expect(...).toPass()`. The dev server still logs `Error: aborted` for the abandoned requests; no test fails on it. `waitForLoadState('networkidle')` was not used: the e2e lint config forbids it.
- T13: the first two `pnpm verify` runs failed one task, `@byteflock/admin-dashboard:build`, with `A required privilege is not held by the client. (os error 1314)`. The build itself succeeded; the error came after it, when Nx stored the build outputs (`.next/**`) in its local cache. Since `pg` arrived (T03), Turbopack links it into `.next/node_modules/pg-<hash>` as an external package; Nx's cache recreates that link as a symlink, and Windows refuses symlinks without Developer Mode or the privilege. It looked flaky (Nx said so) only because every manual retry used `--skip-nx-cache`; with the cache on it fails every time. Fix: `"cache": false` on the dashboard's `build` target (`apps/admin-dashboard/package.json`), so Turbopack always creates its own links; Next keeps its incremental cache in `.next/cache`. Rejected: leaving `.next/node_modules` out of the cached outputs (a cache hit would restore a build without its `pg` link and `next start` could fail). Enabling Windows Developer Mode would also avoid it but is a machine setting for the product owner to decide, not a repository change.
- T13: the P1.6 smoke test `/dev/session switches tenants in one click` failed once on a cold `next dev` (the click was swallowed by a reload, as in T12). The retrying switcher click is now a shared helper, `signInWithSwitcher`, used by that test, the platform test and the dev-session spec.
- T14: `pnpm visual` (P1.7-T03) broke with P2.1 and is fixed here: the dashboard's visual tests now need Postgres, which the pinned Linux container could not reach. `tools/scripts/visual.mjs` now starts the database, recreates a dedicated `byteflock_visual` database (so local publishes never change the screenshots), and gives the container `--add-host=host.docker.internal:host-gateway` with the three database URLs. The run then showed one changed snapshot, `home-acme-chromium-linux.png`; the diff was only the intended P2.1 changes (heading `Acme Corp support` from the T09 config title, the `Dashboard` nav entry from T09, the role in the dev badge from T12; colours and layout identical). It was regenerated with `pnpm visual --update`, reviewed, and a fresh `pnpm visual` passed all nine snapshots (5 playground, 4 dashboard).
- T15: the e2e suite now runs on `byteflock_test` (the spec) when Playwright starts the servers. When a running `pnpm stack` is reused, it runs on the stack database `byteflock`, as before T15, because that is what the reused server reads; global setup resets it. That reuse path was not exercised in this task. The jest DB suites `db.spec` and `request-context.spec` also use `byteflock_test`; they and the e2e suite must not run at the same time (verify and CI run them one after the other).
- T16 (open, for the product owner): spec section 9 step 7 expects "a clear error page, no stack trace" when the database is down. The dashboard has no `error.tsx` or `global-error.tsx`, so in development Next.js shows its error overlay with the connection error and a stack trace (no tenant data is shown). The runbook step says what actually happens instead of the spec's wording; it was not re-run in a browser for this task. Adding an error page is product work, not documentation; it is left for the product owner to schedule (in P2.1 before acceptance, or a later phase).
- T16: the owner role `byteflock` is the Postgres image's superuser, so it bypasses row-level security even where it is forced; only `byteflock_app` (what the dashboard uses) is bound by it. The developer guide says so and shows how to query as the app role.
- T17: the lint `jsx-a11y` rules (from Nx's React preset) are warnings, not errors, so they never failed lint; the report counts them and says so. Making them errors is left to the product owner.
- T17: the first run of the new pipeline ran every task cold (the `nx.json` change alters every hash), and `P1.2-AC01 is deterministic` in design-tokens hit Vitest's 5 s default under that load (about 1.5 s alone). It now has a 30 s timeout.
- T17: two targets of one project must not share an output folder: Nx restores a cached task's outputs by replacing the folder, which would delete the other target's results. Each target has its own `test-output/reports/<dir>`; `AGENTS.md` says so for new targets.
- T17: the first host-page axe scan reports three `moderate` findings that do not fail the test: `region` and `landmark-one-main` on the playground fixture `clean.html` (its content is not in landmarks), and `landmark-one-main` inside the frame document. The frame finding is a product question (should the conversation frame have a `main` landmark?), left for the product owner.
