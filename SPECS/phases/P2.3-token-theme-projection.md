## 1. Goal

From the token inventory produced by P2.2, a tenant admin fills the theme editor with their brand: they confirm which source theme is light and which is dark, confirm which token becomes each colour role, see every conversion and drop the theme forces, approve the ones that need approval, and apply. The result is always a valid `theme.v1` theme; saving and publishing work as before.

## 2. Preconditions

1. `SPECS/STATUS.md`: P2.2 is `Accepted`, and P2.3 is `Approved` by the product owner.
2. `pnpm verify --quick` → green.
3. `@byteflock/token-inventory` passes its fixture matrix, including the real samples from P2.2-T01.

## 3. Scope

**In:**

- The projection steps in PROJ-03, in the theme editor's import panel, after the P2.2 extraction screen.
- Choosing light and dark with the evidence and confidence rules of PROJ-04, including picking a mode on other axes (for example the brand) first.
- Role mapping with suggestions, a synonym table and confirmation (PROJ-05).
- Presets from tokens (PROJ-06).
- Blocking rules and lossy-conversion approvals (PROJ-07, PROJ-08).
- The candidate theme and apply-or-cancel (PROJ-09).
- Replacing the baseline single-file importer's internals with layer B, keeping its behaviour for files that follow the convention.
- The projection fixture matrix (PROJ-10) and tests.

**Out:**

- **New theme fields** (spacing scales, custom shadows, custom fonts, extra colour roles). Any of these is a theme contract change with a `CONTRACT-CHANGE:` trailer.
- **Remembering mappings** between imports. Later phase.
- **Server-side projection.** The function is pure and could run on a server later; it does not in this phase.
- **Fixing the default theme's contrast** (§12, risk 3). A separate change.

## 4. Decisions applied

- D-20: imported themes face the same contrast policy as typed ones.
- D-27, D-29: coverage floor, accessibility lint, route budgets.
- P2.2 decisions 1 (two layers) and 6 (nothing leaves the browser).

Decisions fixed by this spec:

1. **Lossy by design, never silently.** Every conversion and drop is listed with its source token (PROJ-08). The inventory and the bundle keep the originals.
2. **Block only on what is used.** Errors in tokens the theme does not use are warnings (PROJ-07).
3. **Component tokens are never suggested for global roles; other namespace tags only rank suggestions** (PROJ-05 rule 3).
4. **The projection entry is separate.** `@byteflock/theme/import` holds layer B, so the widget frame never loads it and other dashboard routes do not either.
5. **Check what is used, not the whole design.** The design tool's audit is not repeated. Projection checks the value of every token it uses, the theme contract and the product's contrast policy (PROJ-07).

## 8. Verification procedure (agent)

1. `pnpm nx run-many -t lint typecheck test -p @byteflock/theme @byteflock/token-inventory @byteflock/admin-dashboard` → green; the projection fixtures are listed.
2. `pnpm nx e2e @byteflock/admin-dashboard-e2e -- --project=chromium --grep "token projection"` → all pass.
3. `pnpm nx build @byteflock/widget`, then search the frame bundle for a symbol only `@byteflock/theme/import` defines → not found.
4. `pnpm verify --quick` → green, including route budgets and the test count.

## 9. Manual validation (human)

On the local stack (`pnpm stack`), signed in as `t_acme` admin, Settings → Theme → Import:

1. For each real sample: extract, confirm light and dark, confirm the mapping, review the projection report, approve if asked, apply. Compare the preview with the design tool in both appearances.
2. Use a sample file that follows the convention (the `single-file` case in the extraction fixtures, EXTRACT-16). It must apply with one click.
3. Cancel at the mapping step. The form must not change.
4. Apply, then reload without saving. The stored theme must not change.
5. Sign in as `t_acme` agent. The import control must not be shown.

## 12. Risks and notes

1. **Role mapping is the hard part.** Deciding which token is `primary` needs judgement. Expect many confirmations at first; AC17 measures them, and the synonym table should grow from real exports.
2. **Lossy projection can surprise.** A tenant may expect their whole design system to apply. The projection report must make clear, in plain words, what the theme can and cannot hold. If tenants need more, that is a theme contract change, decided separately.
3. **The default theme fails contrast today.** `apps/admin-dashboard/src/lib/default-theme.ts` has dark `danger` `#b91c1c` on dark `surface` `#0f172a` at 2.76:1, below THEME-06's 3:1. A partial import onto a tenant with no published theme keeps that pair and cannot be published until it is fixed. It should be fixed separately, before or with this phase.
4. **Open questions for the product owner** (defaults apply if not answered before approval):
   1. Should alpha colours be refused instead of approved with alpha dropped? Default: approve per role.
   2. Should a primitive token be pre-selected for a role when its name matches well? Default: yes, ranked below semantic matches and marked as a primitive (PROJ-05 rule 3).
   3. Should the mapping step allow typing a hex value directly instead of picking a token? Default: no; the form already allows editing after apply.
