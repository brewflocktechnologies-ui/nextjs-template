## 1. Goal

A tenant admin can give the dashboard their design-token export in any structure (one file, several files, a folder or a ZIP) and get back a complete, lossless, traceable **token inventory** with reports, which they can review on screen and download as a bundle. Nothing about the theme changes in this phase: this is layer A of the import, and P2.3 projects its inventory onto the theme.

The import is split in two layers so that both hold: extraction never loses information, and the theme, which can hold far less than a design system, is filled with every loss made explicit.

## 2. Preconditions

1. `SPECS/STATUS.md`: P2.1 is `Accepted`, and P2.2 is `Approved` by the product owner.
2. `pnpm verify --quick` → green.
3. **Real samples.** At least two real exports from the design setup tenants will use (for example a Figma variables export and a Tokens Studio export), anonymised, are available to the implementer. Without them, theme detection and classification rules are guesses (§12).
4. **Baseline.** A single-file importer and an import panel exist, built ahead of these specs on branch `docs/p2.1-tenant-backend-spec` and not yet committed: `libs/theme/src/import-dtcg.ts` and `apps/admin-dashboard/src/app/settings/theme/ImportTokensPanel.tsx`. They keep working through this phase. P2.3 replaces their internals with layer B.

## 3. Scope

**In:**

- Every input kind in EXTRACT-01, with hashing, duplicate detection and canonical ordering.
- The limits in EXTRACT-02.
- Classification of every file by content (EXTRACT-03).
- DTCG recognition (EXTRACT-04), including the 2025.10 check in T01.
- Normalisation of Tokens Studio and Style Dictionary v3 formats (EXTRACT-05).
- Types, values, paths, namespaces and the token record (EXTRACT-06…09).
- References with theme context (EXTRACT-10).
- Theme detection with original identifiers, and the theme-difference report (EXTRACT-11).
- Conflicts and user-confirmed precedence (EXTRACT-13).
- Validation with severities (EXTRACT-14).
- The reports and the downloadable bundle (EXTRACT-12).
- A dashboard screen, in the theme editor's import panel, that runs extraction and shows its summary, reports and bundle download.

**Out:**

- **Filling the theme from the inventory** (choosing light and dark, role mapping, presets). P2.3.
- **Storing** import sets, inventories or bundles on the server, or any new database table. A later phase, if tenants need import history.
- **Remembering** a tenant's precedence answers for a later import. Later phase.
- **Importing from a Figma link** or the Figma API. Later phase.
- **Using** component, spacing, typography or breakpoint tokens anywhere in the product. They are inventoried only.
- **Exporting** the tenant theme as DTCG. A separate feature.

## 4. Decisions applied

- D-27, D-29: the new library and screens are covered by the coverage floor, the accessibility lint, knip and the route budgets.

Decisions fixed by this spec:

1. **Two layers.** Extraction (this phase) is lossless and theme-agnostic. Projection (P2.3) is lossy and theme-specific. They meet only at the inventory.
2. **Content over names.** File, folder and group names are hints, never proof (EXTRACT-03, EXTRACT-11).
3. **Ask, don't guess.** Where the content does not decide (themes or conflict, precedence), the user decides, and the report records the answer.
4. **A new library for layer A.** `libs/token-inventory`, package `@byteflock/token-inventory`, tags `type:lib scope:shared platform:neutral`. It has no DOM, file-system or archive dependency and no dependency on `@byteflock/theme`. `libs/theme` may depend on it in P2.3.
5. **File access in the dashboard.** Reading files, walking folders, unpacking ZIPs, hashing (Web Crypto) and building the bundle ZIP live in `apps/admin-dashboard`.
6. **Nothing leaves the browser.** No route receives import files or inventories in this phase.

## 7. Quality gates introduced

None new. The new library joins the existing gates: lint with tag restrictions, typecheck, Vitest with a coverage floor, knip, the project graph check and the test count. The reproducibility property test runs on every test run.

## 8. Verification procedure (agent)

1. `pnpm nx run-many -t lint typecheck test -p @byteflock/token-inventory @byteflock/admin-dashboard` → green; the fixture tests are listed.
2. `pnpm nx e2e @byteflock/admin-dashboard-e2e -- --project=chromium --grep "token extraction"` → all pass.
3. `pnpm nx build @byteflock/widget`, then search the frame bundle for a symbol only `@byteflock/token-inventory` defines → not found.
4. `pnpm policy:check` → passes, including the project graph and the test count.
5. `pnpm verify --quick` → green, including route budgets.

## 9. Manual validation (human)

On the local stack (`pnpm stack`), signed in as `t_acme` admin, Settings → Theme → Import:

1. Give each real sample from T01 in the form a tenant would receive it (file, folder or ZIP). Check the summary: files, classes, token counts, themes found with their original names.
2. Download the bundle. Check that `source/` holds the original files unchanged and that `validation/validation-report.md` reads correctly.
3. Give a sample with one file renamed misleadingly (`semantic.json` → `dark.json`). Detection must follow content, or ask.
4. Give two files that define the same paths with different values and no theme evidence. The screen must ask "themes or conflict".
5. Check that the theme form did not change at any point.

## 10. Evidence to record

The T01 findings (tools, shapes, the 2025.10 features and how each is handled); the fixture list with pass results; the reproducibility test result; screenshots of the summary, a question and a report view; a sample bundle listing; the AC21 measurements; route budget numbers before and after; one sentence for each new dependency (for example a ZIP library for unpacking and building the bundle: the need, and the alternative considered); every deviation from EXTRACT-01…16.

## 12. Risks and notes

1. **No real samples.** Theme metadata and naming differ between tools and change over time. Building T04, T07 and T08 from invented files would pass the fixtures and fail on real exports. T01 must use real exports, and new ones should become fixtures as tenants bring them.
2. **Scope.** Lossless extraction of every token type, namespace and theme is larger than the theme needs today. The value is that P2.3 and any later consumer (a website stylesheet, a design-system view) build on one trustworthy inventory instead of re-reading files. If time is short, composite-type canonical forms (EXTRACT-07) may be deferred with a note, because the original values are kept anyway.
3. **DTCG is still moving.** T01 checks the current 2025.10 text. Features not supported are reported per token, not dropped.
4. **Heuristic tags.** Namespace tags (primitive, semantic, component) and theme detection without metadata are heuristics. They are labelled with their evidence and never rename or move a token, so a wrong tag costs a review, not data.
5. **Browser memory.** 10,000 tokens with full records and two value forms fit comfortably in a browser tab, but the measurement in AC21 confirms it.
6. **Open questions for the product owner** (defaults apply if not answered before approval):
   1. Which design tools must be supported at exit? Default: Figma variables export and Tokens Studio.
   2. Is ZIP input needed, or is a folder picker enough? Default: both.
   3. Should a conflict be resolvable by choosing a source per path, or only per file? Default: per file, with per-path as a later improvement.
   4. Should import bundles be stored per tenant for history and audit? Default: no, download only, in this phase.
