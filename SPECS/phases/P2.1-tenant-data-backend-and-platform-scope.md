## 1. Goal

Replace the Phase-1 file stubs with a real local data backend: Postgres in Docker, accessed only by the dashboard's Next.js server. Tenants, users, roles, theme drafts, theme revisions, widget settings and a new tenant dashboard config live in the database, and every tenant row is isolated by row-level security. A new **platform scope** lets a super admin see and manage every tenant while the dashboard chrome stays on the platform default design. A **tenant-scoped** login still renders the whole dashboard in that tenant's published design, and the widget still reads static published documents.

## 2. Preconditions

1. `SPECS/STATUS.md`: P1.7 is `Accepted`, and P2.1 is `Approved` by the product owner.
2. `docker version` → prints both client and server versions; `docker compose version` → `v2.x` or later.
3. `pnpm verify --quick` → green on the current `main`.
4. Nothing is listening on port 5440 (`node -e "require('net').connect(5440).on('error',()=>console.log('free')).on('connect',()=>console.log('taken'))"` → `free`).

## 3. Scope

**In:**

- Docker Compose with one Postgres service, and Node scripts to start, migrate, seed and reset it.
- SQL migrations, a migration runner, and seed data built from `validation/tenants.json` plus one super admin.
- A server-only database layer in `admin-dashboard`, with row-level security on every tenant table.
- Moving theme drafts, revisions, the published pointer, widget settings, tenants, users and roles from files into Postgres. The widget's static documents become a projection of the database (materialised on publish).
- Tenant config v1 (contract, guard, table, editor page) for dashboard customisation.
- The platform scope: super admin user, request context union, authorization helper, `/platform/**` pages, the default-chrome rule, and a scoped tenant preview.
- `/dev/session` reads users from the database and offers the super admin.
- Updates to `pnpm stack`, `pnpm stack:reset`, `pnpm verify`, `AGENTS.md` and the local-stack docs.

**Out:**

- **Real authentication** (an identity provider or the chatplatform `accountservice`). The dev adapter stays the only session source. Later phase.
- **A separate backend service** (Node or Java). The Next.js server is the data layer in this phase (D-24).
- **Per-tenant website stylesheet** (`/v1/themes/<tenantId>/current.css`). Later phase; this phase must not block it.
- **Object storage** (S3, MinIO) for published documents. The widget's static folder stays the publish target in development (D-13).
- **Audit log, approval workflows, user management UI, invitations, billing.** Super admin can view and edit tenant theme, tenant config and widget settings only.
- **Agent inbox and conversation data.** No conversation tables.
- **Production deployment** of Postgres, backups, connection pooling services.

## 4. Decisions applied

D-11, D-12 (amended by D-25), D-13 (amended by D-24), D-20 (amended by D-25), D-21, D-22, D-24, D-25. Fixed by this spec:

### 4.1 Database and tooling

- **Postgres 17**, one Compose service `db` in `compose.yaml` at the repository root, image pinned by tag **and** digest. Host port **5440** (avoids clashes with other local Postgres instances), named volume `byteflock-pg`.
- Two databases on that server: `byteflock` (the stack) and `byteflock_test` (tests; dropped and recreated by test setup).
- Development connection string, committed in `apps/admin-dashboard/.env.development`: `DATABASE_URL=postgres://byteflock:byteflock@localhost:5440/byteflock`. These are local-only credentials; production values never live in the repository.
- Client library: **`pg`** (node-postgres) with parameterised queries. **No ORM and no query builder.**
- Migrations: plain SQL files in `apps/admin-dashboard/db/migrations/NNNN_<name>.sql`, applied in order by a Node runner (`tools/scripts/db/migrate.mjs`) that records them in a `schema_migrations` table inside a transaction per file. Migrations are forward-only; an applied file must not be edited (a checksum mismatch fails the runner).
- All database scripts are Node (`tools/scripts/db/*.mjs`) and call `docker compose` through `child_process` with `path.join` paths. No shell scripts.

### 4.2 Schema (initial migration)

| Table                | Columns (essentials)                                                                                                                                        | Rules                                                                                      |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `tenants`            | `tenant_id text pk` (`^t_[a-z0-9_]{2,40}$` check), `name`, `published_revision int null`, `created_at`                                                      | `published_revision` references `theme_revisions` for the same tenant                      |
| `users`              | `user_id text pk` (`^u_[a-z0-9_]{2,40}$`), `display_name`, `locale`, `platform_role text null` (`'super_admin'` or null), `created_at`                      |                                                                                            |
| `tenant_memberships` | `user_id`, `tenant_id`, `role` (`'tenant_admin'` or `'agent'`), pk `(user_id, tenant_id)`                                                                   | A user with `platform_role` must have no memberships (check via trigger)                   |
| `widget_keys`        | `widget_key text pk` (`^wk_[a-z0-9_]{2,60}$`), `tenant_id`, `allowed_origins text[]` (1–20), `locale_default`, `locales_supported text[]`, `features jsonb` | `allowed_origins` validated per ENDP-02a in the data layer before insert                   |
| `theme_drafts`       | `tenant_id pk`, `doc jsonb`, `updated_at`, `updated_by`                                                                                                     |                                                                                            |
| `theme_revisions`    | `tenant_id`, `revision int`, `doc jsonb`, `schema_version int`, `published_at`, `published_by`, pk `(tenant_id, revision)`                                  | **Immutable**: a trigger rejects `UPDATE` and `DELETE`. Revisions are monotonic per tenant |
| `tenant_configs`     | `tenant_id pk`, `doc jsonb`, `schema_version int`, `updated_at`, `updated_by`                                                                               | `doc` passes the tenant-config guard before write                                          |

Every table that has a `tenant_id` column must have **row-level security enabled and forced**, with one policy:

```sql
USING (
  current_setting('app.scope', true) = 'platform'
  OR tenant_id = current_setting('app.tenant_id', true)
)
```

The application connects as a role (`byteflock_app`) that is **not** the table owner and has no `BYPASSRLS`. Migrations and seeds run as the owner role (`byteflock`).

### 4.3 Request scope (ADR-013, replaces the ADR-005 context shape)

```ts
type RequestContext = { scope: 'tenant'; tenantId: string; userId: string; roles: TenantRole[]; locale: string } | { scope: 'platform'; userId: string; roles: ['super_admin']; locale: string };
```

- The dev session cookie carries only `{ userId, tenantId | null, iat }`, signed as today (D-12 format otherwise unchanged). On every request the server loads the user, their `platform_role` and their membership from the database. A role change takes effect on the next request; a cookie for a deleted user or a missing membership yields no context.
- A user with `platform_role = 'super_admin'` always gets `scope: 'platform'`, whatever `tenantId` the cookie holds.
- **One query path.** Every database call goes through `withScope(ctx, fn)`, which opens a transaction and runs `SET LOCAL app.scope` and `SET LOCAL app.tenant_id` before `fn`. Code outside `src/server/db/**` must not import `pg`.
- **One authorization helper.** `authorize(ctx, tenantId, action)` with `action` in `theme.read | theme.write | theme.publish | config.read | config.write | widget.read | widget.write | tenants.list`. Tenant scope: allowed only when `ctx.tenantId === tenantId` and the role permits the action (`agent` gets the `*.read` actions only). Platform scope: allowed for every action. Every route handler and server action calls it before any data access; it throws a typed `ForbiddenError` mapped to HTTP 403.
- The `data-access-tenant-first` lint rule stays for `src/data/**`. Platform-only functions (only `listTenants` in this phase) live in `src/data/platform/**` and take `ctx: PlatformContext` first; the rule is extended to accept exactly that.

### 4.4 Chrome rule (D-25)

- **Platform scope:** the root layout always emits the platform default variables (`DEFAULT_VARS`), whatever page the super admin is on, including pages about a specific tenant.
- **Tenant scope:** the root layout emits the tenant's published theme exactly as P1.6-T04 does (D-20 unchanged for tenant scope).
- **Scoped tenant preview:** on `/platform/tenants/[tenantId]/**` the tenant's resolved variables are applied only to a preview container (`<TenantPreview tenantId>`) through a nonce'd `<style>` that targets `[data-tenant-preview="<tenantId>"]`, never `:root`, `html` or `body`. The container shows a sample of dashboard components and carries a visible label "Preview: <tenant name>". The widget preview iframe works as in P1.6.
- A super admin who opens a tenant route (`/`, `/settings/**`) is redirected to `/platform`. A tenant user who opens `/platform/**` gets 404 (not 403, so the route's existence is not revealed).

### 4.5 Publish (THEME-09, D-13 amended by D-24)

`publish(tenantId)` runs in one transaction: validate the draft and run the contrast policy → insert the next `theme_revisions` row → set `tenants.published_revision` → commit. **After** commit it materialises the static documents into `THEME_PUBLISH_DIR`: theme file first, then `config/<widgetKey>.json` (`themeRevision`), keeping the THEME-09 order and the existing atomic writes. Postgres is the source of truth. If materialisation fails, the publish still stands and `pnpm db:materialise` rebuilds every static document from the database; `rollback` only moves `published_revision` and re-materialises the config pointer.

### 4.6 Tenant config v1 (CONFIG, new contract)

A small, versioned document for dashboard customisation, read only by the dashboard (never by the widget):

```jsonc
{
  "schemaVersion": 1,
  "modules": { "themeEditor": true, "widgetSettings": true }, // nav entries and routes shown to tenant users
  "defaults": { "locale": "en-AU" }, // must be one of the tenant's supported locales
  "home": { "title": "Acme support", "notice": "Office closed Friday" }, // plain text, ≤ 60 and ≤ 200 chars
}
```

Rules: unknown keys rejected; strings are plain text rendered as text, never HTML; a disabled module hides its nav entry **and** makes its routes return 404 for tenant users (platform scope always sees every module). Missing or invalid config falls back to the defaults above, logged, never thrown at render. The contract file defines CONFIG-01…06 (shape, limits, fallback, versioning, who may write, migration rule).

## 8. Verification procedure (agent)

1. `pnpm install --frozen-lockfile` → clean.
2. `pnpm db:reset` → prints migrations applied and seed counts (3 tenants, 5 users including `u_platform_admin` and `u_acme_agent`).
3. `pnpm db:migrate` → "0 migrations applied".
4. `pnpm nx run-many -t lint test typecheck -p @byteflock/admin-dashboard` → green, including the authorization matrix and RLS tests.
5. `pnpm stack` in one terminal; `pnpm stack:check --wait 120` → all origins and the database reported OK.
6. `pnpm nx e2e @byteflock/admin-dashboard-e2e --project=chromium` → green; output contains `P2.1-AC05`, `P2.1-AC06`, `P2.1-AC08`, `T-04`.
7. Editor flow as super admin: `pnpm nx e2e @byteflock/admin-dashboard-e2e --grep "platform publish"` → green; `pnpm policy:check` → fails on `check-no-local-publish`; `pnpm stack:reset` → passes again.
8. Materialisation repair: run the `--grep "materialise repair"` test → green.
9. `NODE_ENV=production pnpm nx run @byteflock/admin-dashboard:build` then `start`; request `/dev/session` → 404; `NODE_ENV=production pnpm db:seed` → non-zero exit.
10. `pnpm verify` → green; paste the summary table into the evidence file.

## 9. Manual validation (human)

## 12. Risks and notes

- **Docker on Windows.** Docker Desktop needs WSL2 and can be slow to start. `db:up` must wait on the healthcheck and say clearly when Docker isn't running, rather than failing later in a test.
- **RLS and pooling.** Session variables must be set with `SET LOCAL` inside a transaction; a plain `SET` on a pooled connection would leak one tenant's scope into the next request. `withScope` is the only allowed path, and a test runs two tenants' queries interleaved on a pool of size 1.
- **Next.js 16 runtime.** `pg` needs the Node.js runtime; it must never load in `proxy.ts` (already restricted by the `proxy-allowlist` rule) or in an edge route. Check `node_modules/next/dist/docs/` for the current runtime and `serverExternalPackages` guidance on the day.
- **Static projection drift.** If a publish commits but materialisation fails, the widget shows the previous revision until `db:materialise` runs. Acceptable in development; production storage (later phase) must make this transactional or retried.
- **Super admin power.** A super admin can change any tenant's theme and config. Without an audit log (out of scope) these changes are only traceable through `published_by` and `updated_by`. The audit log should be the first follow-up.
- **Scope creep.** User management, invitations and real login are tempting once users live in a table. They are out (§3).

  2. Should `agent` users see the dashboard at all in this phase? Default: yes, read-only settings.
  3. Should the per-tenant website stylesheet come next, or real authentication? Default: real authentication.
